# DCVS API Contract

**Status:** Contract for the updated 9-file Oracle/ORDS SQL package  
**ORDS module:** `dcvs.api`  
**Base URL (local):** `http://localhost:8080/ords/dcvs/api`  
**Frontend environment variable:** `VITE_API_BASE_URL`  
**Important:** `VITE_API_BASE_URL` must not end with `/`.

This document describes the routes defined by `09_ords_modules.sql` and the payload conventions used by the PL/SQL packages. Treat it as the frontend integration reference. If a route or field has not been confirmed by an actual API test, verify it against the running ORDS deployment before relying on it.

## 1. Request and response conventions

- Send and receive JSON for JSON endpoints.
- Protected endpoints require `X-Auth-Token: <token>`.
- Login is public. `POST /verify` is public; a token is optional and may be sent when a verifier is logged in.
- Dates use `YYYY-MM-DD`.
- JSON field names use `snake_case`.
- Success envelope: `{"success":true,"data":...}`.
- Error envelope: `{"success":false,"error":"message"}`.
- Expected HTTP status meanings: `200` success, `201` created (where returned), `400` invalid request, `401` missing/invalid authentication, `403` role/scope denied, `404` missing resource, `409` duplicate/conflict. Actual status is determined by each PL/SQL handler.

## 2. Authentication

| Method | Path | Access | Request | Response / purpose |
|---|---|---|---|---|
| GET | `/ping` | Public | — | Basic API ping |
| GET | `/health` | Public | — | Health response |
| POST | `/auth/login` | Public | `{"username":"...","password":"..."}` | `data` contains `token`, `expires_in`, and `user:{account_id,username,user_type,linked_id}` |
| POST | `/auth/logout` | Authenticated | `X-Auth-Token` | Invalidates/logs out the current token |
| GET | `/auth/me` | Authenticated | `X-Auth-Token` | Returns the current account details |

Token lifetime returned by the current login implementation is expressed in seconds. The observed admin login response returned `expires_in: 7200`.

## 3. Resource endpoints

The following routes are registered in `09_ords_modules.sql`. `:id` is a path parameter.

| Resource | Registered methods and paths | Access intent |
|---|---|---|
| Applicants | `GET /applicants`, `POST /applicants`, `GET /applicants/:id`, `PUT /applicants/:id`, `DELETE /applicants/:id`, `GET /applicants/:id/certificates` | List: ADMIN, HR, VERIFIER. Individual read is scoped; an APPLICANT may read their own record. Create: ADMIN. Update: ADMIN or own APPLICANT where permitted. Delete: ADMIN. |
| Certificate types | `GET /types`, `POST /types`, `GET /types/:id`, `PUT /types/:id`, `DELETE /types/:id` | Read: authenticated roles allowed by the handler. Write: ADMIN. |
| Issuers | `GET /issuers`, `POST /issuers`, `GET /issuers/:id`, `PUT /issuers/:id`, `DELETE /issuers/:id`, `GET /issuers/:id/certificates` | ADMIN. Issuer `public_key` is generated by the database and is read-only. |
| Certificates | `GET /certificates`, `POST /certificates`, `GET /certificates/:id`, `PUT /certificates/:id`, `DELETE /certificates/:id`, `POST /certificates/:id/issue`, `POST /certificates/:id/revoke`, `GET /certificates/:id/qr`, `GET /certificates/:id/signature` | Reads are scoped by role and ownership; mutations are ADMIN-only. Editing/deleting is restricted to certificates that have not been issued. |
| Revocations | `GET /revocations`, `GET /revocations/:id` | ADMIN. |
| Verifiers | `GET /verifiers`, `POST /verifiers`, `GET /verifiers/:id`, `PUT /verifiers/:id`, `DELETE /verifiers/:id`, `GET /verifiers/:id/verifications` | List: ADMIN and HR's managed verifiers. Read: ADMIN, managing HR, or the verifier themself. Create/delete: ADMIN. Update: ADMIN or managing HR. |
| HR | `GET /hr`, `POST /hr`, `GET /hr/:id`, `PUT /hr/:id`, `DELETE /hr/:id`, `GET /hr/:id/verifiers` | ADMIN; HR may read their own record and managed verifiers. |
| Verification records | `GET /verifications`, `GET /verifications/:id` | ADMIN (all), VERIFIER (own), HR (their managed verifiers' records). |
| Dashboard | `GET /dashboard/stats`, `GET /dashboard/certificates`, `GET /dashboard/verifications` | ADMIN. |

### Applicant request fields

Create/update body:

```json
{
  "first_name": "Asha",
  "middle_name": "M",
  "last_name": "Nair",
  "dob": "2004-01-15",
  "aadhar_card": "000000000000",
  "street": "Example Street",
  "city": "Bengaluru",
  "state": "Karnataka",
  "pincode": "560001",
  "emails": ["asha@example.com"],
  "phones": ["9000000000"],
  "username": "asha",
  "password": "change-this"
}
```

`username` and `password` are optional together when creating a linked login account. Do not send passwords in read/update responses.

### Certificate type request fields

```json
{"type_name":"Degree Certificate","description":"Academic degree"}
```

### Issuer request fields

```json
{
  "issuer_name": "Example University",
  "organisation": "Example University",
  "email": "issuer@example.com",
  "phone": "9000000000",
  "street": "Example Road",
  "city": "Bengaluru",
  "state": "Karnataka",
  "pincode": "560001"
}
```

`public_key` is generated by the database; clients must treat it as read-only.

### Certificate request fields

Create body:

```json
{
  "title": "B.Tech Degree Certificate",
  "applicant_id": 1,
  "type_id": 4,
  "issuer_id": 3,
  "issue_date": "2026-11-08",
  "expiry_date": null,
  "document_url": null,
  "upload_certificate": null
}
```

Issuance is a separate action: `POST /certificates/:id/issue`. The database computes and stores the certificate hash, digital signature, and QR verification URL.

Revoke body:

```json
{"reason":"Issued by mistake"}
```

The reason should be meaningful; the contract's validation target is at least 5 characters. Re-revoking a certificate should be treated as a conflict.

Signature endpoint response fields:

```json
{
  "certificate_hash": "...",
  "digital_signature": "...",
  "hash_valid": true,
  "signature_valid": true
}
```

QR endpoint response fields:

```json
{"certificate_no":"DCVS-2026-001","verify_url":"http://localhost:5173/verify?ref=DCVS-2026-001"}
```

## 4. Public certificate verification

| Method | Path | Access |
|---|---|---|
| POST | `/verify` | Public; optional `X-Auth-Token` |

Request:

```json
{
  "reference": "DCVS-2026-001",
  "method": "MANUAL"
}
```

Allowed methods: `MANUAL`, `QR`, `API`. If omitted, the PL/SQL handler defaults to `MANUAL`.

The response is a success envelope whose `data` is the verification result. The verification data includes a result, message, certificate details when found, and hash/signature validity indicators. Expected result values are `VALID`, `INVALID`, `EXPIRED`, `REVOKED`, or `TAMPERED`.

Example request from Bash:

```bash
export BASE="http://localhost:8080/ords/dcvs/api"

curl -i -X POST "$BASE/verify" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"reference":"DCVS-2026-001","method":"MANUAL"}'
```

For an authenticated verifier session, add:

```bash
-H "X-Auth-Token: $TOKEN"
```

## 5. Certificate response fields

Certificate list/detail responses include the fields returned by the certificate detail view/package, including:

`certificate_id`, `certificate_no`, `title`, `applicant_id`, `applicant_name`, `type_id`, `type_name`, `issuer_id`, `issuer_name`, `organisation`, `issue_date`, `expiry_date`, `document_url`, `upload_certificate`, `qr_code`, `digital_signature`, `certificate_hash`, `is_issued`, `status`, `revocation_reason`, `revoked_date`.

Known status values: `DRAFT`, `VALID`, `EXPIRED`, `REVOKED`. `is_issued` is a Boolean.

## 6. Dashboard response shapes

- `GET /dashboard/stats`: aggregate counts such as `total_certificates`, `valid`, `expired`, `revoked`, `draft`, `total_verifications`, `total_applicants`, `total_issuers`, and `total_verifiers`.
- `GET /dashboard/certificates`: grouped arrays `by_month`, `by_type`, `by_issuer`, `by_status`; each item uses `label` and `count`.
- `GET /dashboard/verifications`: grouped arrays `by_day`, `by_result`, `by_method`; each item uses `label` and `count`.

## 7. Frontend integration notes

- Build the base URL from `import.meta.env.VITE_API_BASE_URL`.
- Do not append a trailing slash to the configured base URL.
- Store the login token using the frontend's chosen session strategy; attach it as `X-Auth-Token` on protected requests.
- Handle the standard success/error envelope and HTTP status codes.
- Do not assume pagination, filtering, or search parameters are supported by ORDS. The current project contract expects the frontend to filter, sort, and paginate returned lists client-side.
- Do not hardcode the local QR URL for production. Configure the frontend verification URL for the deployment environment.
- Treat `aadhar_card`, contact details, password values, auth tokens, digital signatures, and certificate hashes as sensitive. Do not log them unnecessarily or expose them in public UI.
- The API and database should be tested route-by-route after running `09_ords_modules.sql`; a route being listed here does not prove that it has been tested against the current running database.

## 8. Deployment reminder

The updated SQL package defines the ORDS module `dcvs.api` with base path `/api/`. The schema must be ORDS-enabled with schema alias `dcvs`. Re-running `09_ords_modules.sql` deletes and recreates that module's route definitions. It does not mean the frontend has been deployed or that all endpoints have been integration-tested.
